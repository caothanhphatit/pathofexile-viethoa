# Migrations

SQL migrations are plain `*.sql` files named `NNN_description.sql` (zero-padded
sequence prefix). They are applied in lexical order by `src/db/migrate.mjs`,
which records each applied file plus a SHA-256 checksum in the
`schema_migrations` table.

## Why rationale lives here instead of inline comments

Migration content is checksummed once applied. Editing an already-applied
`.sql` file (even to add a comment) changes its checksum and makes
`migrate.mjs` throw `Migration checksum changed: <file>`. To document the
*why* behind existing migrations without triggering checksum drift, the
business context is recorded in this README rather than edited into the
applied files. New / not-yet-applied migrations may still carry inline
comments freely.

`migrate.mjs` also runs a non-destructive `validateMigrationSequence` check at
startup that logs (does not fail) when sequence numbers are missing or
duplicated.

## Migration rationale

### 003_drop_legacy_localization.sql (DESTRUCTIVE)

Drops the first-generation localization scaffolding that predates the
current content model:

- Drops `idx_items_translated_gin` and the `items.translated_json` column —
  the inline per-row translation blob was replaced by the normalized
  localization tables introduced in `002_content_localization.sql`.
- Drops the `skill_gem_translations` table and the `summary_vi` /
  `description_vi` columns on `skill_gem_details` / `currency_items` — these
  ad-hoc Vietnamese columns were superseded by the generalized content
  localization layer.

This migration is destructive (drops a table and columns). It is retained as
historical schema evolution; it should never be re-run against a database
where it has already been applied (the checksum guard enforces this). If
rebuilding from scratch, the data it removed is regenerated by the crawl/
export pipelines, not preserved.

### 011_game_entity_typed_indexes.sql (index strategy)

Adds partial, expression-based indexes over `game_entities`,
`game_assets`, and `game_entity_relations`. The strategy:

- **Partial indexes** (`where entity_type = '...'` / `where kind = '...'` /
  `where relation_type = '...'`): each game entity type (item_base, mod,
  active_skill, passive_node, stat, monster_variety, world_area,
  crafting_recipe, endgame_map, etc.) has very different query shapes, so a
  narrow per-type index is far smaller and more selective than one wide index
  over the whole table.
- **Expression indexes on `normalized_json ->> 'key'`**: the hot filter/sort
  columns (e.g. `item_class`, `drop_level`, `level`, `domain`, `notable`)
  live inside the JSON payload. Indexing the extracted text expression lets
  the planner use the index for the lookups the public read endpoints
  actually issue.
- **Leading `extract_version_id` + `lower(display_name)`**: queries are
  always scoped to a single extract version and frequently search by
  case-insensitive name, so those lead the composite keys; trailing
  `entity_key` keeps each index covering for key-only fetches.

All indexes use `create index if not exists`, so the migration is idempotent
and safe to include in a fresh build.
