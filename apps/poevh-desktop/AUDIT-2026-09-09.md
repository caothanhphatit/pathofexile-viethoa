# POEVH source audit — 2026-09-09

## Verification result

- `cargo test --workspace`: 130 passed, 0 failed, 2 ignored.
- `cargo clippy --workspace --all-targets -- -D warnings`: passed.
- Ignored tests require a live supported PoE2 process or the live GGG Trade2 API.

Passing unit tests do not prove the current multi-process controller topology or
portal handling in the live game.

## P0: blocks the requested two-client topology

1. Controller allocation is fixed at two virtual pads for every bound instance.
   A native-WASD main plus one two-character follower client therefore creates
   four pads instead of two.
2. The main profile always contributes its second character as a follower. There
   is no explicit `NativeKbm` versus `CouchCoop2` input mode.
3. `GameStateReader` attaches to the first matching PoE process returned by the
   Windows process snapshot, not the PID bound as the runtime main instance.
   With multiple clients, leader, follower, terrain and loot data may come from
   the wrong process.
4. Portal recovery is not a confirmed state machine. `WarpToMain` sends D-pad
   Down, while the manual portal command broadcasts A. Neither detects a portal,
   confirms loading, confirms the destination area, or performs bounded retry.

## P1: real implementation with incomplete production data or lifecycle

- Auto-pickup has a real memory-reader, filter, movement, controller-input and
  entity-disappearance confirmation path. It still depends on deterministic PID
  binding and character-to-pad mapping before it can be trusted across clients.
- Smart Follow uses asynchronous route calculation and validates cached routes,
  but its input destination inherits the same controller/PID topology problem.
- Expedition scanning is real, but the bundled combination catalog contains only
  four fallback recipes; it is not a complete current-game catalog.
- Per-process graphics apply is explicitly unsupported. The server correctly
  rejects the command instead of pretending it succeeded.
- Standalone login calibration is intentionally unavailable through the current
  API. Profile credentials are not sufficient to make the full login flow ready.

## P2: cleanup and product integrity

- Production command routing still exposes `spawn_loot` and `spawn_threat` debug
  commands. The live adapter ignores them, but they should be compiled behind a
  development feature or removed from production routing.
- `MockWorldAdapter` remains useful for tests, but production startup and UI must
  never present mock state as verified live telemetry.
- Old architecture and review documents describe intermediate states. Treat this
  audit and executable tests as newer evidence, then archive superseded documents
  once the P0 refactor is complete.

## Required architecture before live acceptance

1. Add an explicit per-runtime input topology: `NativeKbm` or `CouchCoop2`.
2. Allocate zero virtual pads for a native-WASD main and exactly two pads for the
   follower client; do not derive global pad names from profile IDs.
3. Construct/reconnect the memory reader with the verified bound main PID.
4. Persist explicit character-to-runtime-pad assignments and fail closed when a
   configured character cannot be matched.
5. Implement a portal transition state machine with detection and confirmation.
6. Add an integration test for one native main plus one two-character follower
   client, followed by a live validation of follow, loot and area transition.
